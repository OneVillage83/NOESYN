# NOESYN Engineering Record — Phase 1A

- **Timestamp:** 2026-09-03T02:01:09-07:00
- **Phase:** 1A — Source Contracts & Stack Evaluation
- **Result:** COMPLETE — implementation baseline frozen
- **Next:** Phase 1B — Core Identity Persistence & First Metadata Vertical Slice

## Objective

Continue from the Phase 0 architecture freeze candidate and resolve the implementation/source decisions that were intentionally left open before any production application scaffold is created.

The work had two required outcomes:

1. verify real scholarly-provider contracts from current official documentation so NOESYN does not encode remembered/stale API behavior or unsafe rights assumptions;
2. select the durable application/storage/orchestration stack against Phase 0 invariants rather than letting the first framework installed define the architecture.

## Source contract research and decisions

### Crossref

Verified current official REST/API documentation including:

- public REST metadata access;
- identified/polite access using contact information;
- current rate-limit structure following the 2025-12-01 update;
- separate single-record versus list/query rate/concurrency limits;
- cursor paging for deep traversal;
- recommendation to cache responsibly and use official public data files/snapshots at corpus scale;
- link/TDM fields do not themselves grant access or reuse permission.

Official material:

- https://www.crossref.org/documentation/retrieve-metadata/rest-api/
- https://www.crossref.org/documentation/retrieve-metadata/rest-api/access-and-authentication/
- https://www.crossref.org/documentation/retrieve-metadata/rest-api/tips-for-using-public-data-files-and-plus-snapshots/
- https://www.crossref.org/blog/update-to-rest-api-rate-limits/

Decision: Crossref is the initial DOI-centric publisher/member-deposited metadata backbone.

Contract commit: `a91360750e1e2cc767b7e4c8441f59fb1f2067f9`.

### OpenAlex

Verified current official documentation including:

- API key/budget model;
- API paging/deep cursor behavior;
- current request-rate ceiling and account budget mechanics;
- broad work/author/institution/source/topic graph;
- official full snapshot and incremental/update path;
- metadata under CC0;
- OA/location license fields are location-specific evidence;
- original PDFs/full text retain their underlying copyright/licenses;
- incremental sync must be supplemented by reconciliation for upstream merges/deletions.

Official material:

- https://docs.openalex.org/
- https://docs.openalex.org/how-to-use-the-api/
- https://docs.openalex.org/download-all-data/openalex-snapshot
- https://openalex.org/pricing

Decision: OpenAlex is the preferred broad scholarly-graph complement to Crossref.

Contract commit: `f69d4e2e3aed4e8ee0a75888502008416b3b9498`.

### Semantic Scholar

Verified current Academic Graph / Recommendations / Datasets API families and current API/data-license constraints.

Key finding: Semantic Scholar remains strategically useful, but broad persistent dataset/commercial production use should not be assumed safe merely because an API exists. API/data and underlying third-party content licenses are distinct.

Decision: retain as strategic enrichment source; production bulk/persistent commercial use is fail-closed until the applicable AI2 license is explicitly approved and recorded.

Contract commit: `b5ba6edc2829af0520f44a2285d6ed5163ea2cb6`.

### Unpaywall

Verified:

- current v2 DOI API;
- email parameter requirement;
- 100,000 calls/day published guidance;
- OA-location/version/license fields;
- `is_oa`/`oa_status` are access classifications, not broad reuse permission;
- provider's current bulk direction is integrated with OpenAlex rather than relying on the old standalone snapshot assumption for new integrations.

Decision: Unpaywall is a focused DOI access resolver; broad new OA synchronization aligns with OpenAlex where appropriate.

Contract commit: `a2661cc617b10248f9831816a740946b33101860`.

### PubMed / NCBI

Verified E-utilities behavior including:

- PubMed ESearch/EFetch/ESummary/ELink/EPost/History workflows;
- NCBI `tool`/`email` identification;
- current default request-rate guidance (3 requests/second without key; 10 with API key unless approved otherwise);
- recommendation to batch/history and schedule large jobs outside peak periods;
- abstract availability does not imply unrestricted copyright reuse.

Decision: separate PubMed bibliographic/MeSH identity role from PMC full-text/document role.

Contract commit: `f4a3f0817dcbb6bf76847d49218e1d9ba8744c1b`.

### PubMed Central

Verified:

- current developer service set;
- modern OAI-PMH endpoint `https://pmc.ncbi.nlm.nih.gov/api/oai/v1/mh/`;
- approved automated retrieval routes rather than page scraping;
- Open Access Subset/JATS/Cloud/OAI mechanisms;
- article/collection licenses vary;
- presence in PMC does not mean unrestricted reuse;
- machine-readable full text and author manuscripts have different rights classes.

Decision: PMC is a structured JATS/full-text source only under exact article/version/collection/action rights.

Contract commit: `39e92d36b09876fd4a589304362d2a025fcdb1e3`.

### Europe PMC

Verified current REST/OAI/bulk developer paths, OA full-text XML capability, citation/reference/status/grant/annotation enrichment and the explicit distinction between OA bulk content and non-open records.

A single universal current REST requests-per-second number was not found in the main official documentation reviewed, so the contract requires a conservative configurable throttle and re-verification before production instead of inventing a quota.

Decision: complementary life-science discovery/graph/permitted full-text source.

Contract commit: `58e6f8d16a326169f35b09b26d09b36363147506`.

### CORE

Verified current official CORE API, FAQ and Terms.

Critical finding:

- CORE supports commercial API/product use under applicable licensing;
- current terms specifically require contact/licensing for products that may be monetized or overlap API/search/discovery/recommendation/analytics functions;
- API page documents baseline request-rate behavior and higher registered/VIP tiers;
- underlying article/repository rights remain separate from CORE service/data licensing.

Decision: CORE remains strategically important for repository/non-DOI/full-text discovery but production commercial integration is fail-closed until the applicable CORE license is approved/recorded.

Contract commit: `d8c629fe18b1e29abe7222f50cb30d3944f25591`.

### arXiv

Verified current API user manual, bulk-data guidance and license documentation.

Critical findings:

- exact `vN` versions must be preserved;
- query API is not the bulk-corpus mechanism;
- OAI-PMH is preferred for bulk metadata and official S3/Kaggle mechanisms exist for bulk data;
- current guidance encourages delays between API requests;
- default arXiv distribution license does not grant NOESYN blanket third-party redistribution rights;
- different arXiv versions can have different licenses.

Decision: arXiv is the version-aware preprint source and a first-class proof case for WorkVersion/license versioning.

Contract commit: `e7d80b94929d1785aa25d80fd11712e0b5f8ed00`.

## Source architecture result

Accepted initial universal metadata pair:

> **Crossref + OpenAlex**

Reasons:

- complementary DOI exact/deposit + broad graph roles;
- current metadata terms suitable for a durable local source-observation corpus;
- official bulk/snapshot paths;
- avoids making a still-license-gated enrichment dataset the Phase 1 canonical metadata dependency.

Accepted search/discovery approach:

> **Hybrid local-first** — local synchronized/canonical metadata first, permitted provider expansion second, provider bulk snapshots/incremental sync at scale.

NOESYN must not permanently require an external provider call for every user search.

Source-decision ADR commit: `87a33710c37d968f541e9334187d7f8167cab72e`.

## Stack evaluation

### Backend language/framework

Evaluated Python-only, TypeScript-only and mixed Python/TypeScript.

Selected:

- Python 3.14 line;
- FastAPI;
- Pydantic boundaries;
- SQLAlchemy 2.x + Alembic;
- async-safe source clients;
- TypeScript/Next.js frontend;
- generated TypeScript client from FastAPI OpenAPI.

Rationale:

- Python owns scholarly parsing/scientific/ML/evaluation workloads;
- TypeScript/React owns the complex browser reader;
- OpenAPI is a testable language-neutral transport boundary;
- no premature physical microservice requirement.

Official materials included Python 3.14 UUID documentation and current FastAPI OpenAPI documentation.

ADR commit: `48faccc4df16198d4e0ca92d80cab03cfec99e72`.

### Canonical database

Selected PostgreSQL 18+.

Verified current official PostgreSQL 18 support for:

- native UUID type;
- native `uuidv7()`;
- native full-text search;
- strong relational/transaction semantics needed by identity/provenance.

Decision: PostgreSQL is canonical state and initial search/graph edge store. Specialized search/vector/graph systems are later rebuildable projections.

### Internal IDs

Selected UUIDv7.

Current Python 3.14 and PostgreSQL 18 both provide standard UUIDv7 support.

Rules:

- UUIDv7 is opaque internal/durable identity;
- explicit timestamps remain authoritative;
- external provider IDs remain typed aliases;
- UUID ordering is never treated as domain meaning.

### Provenance persistence

Selected append-oriented relational source observations/dependencies plus materialized current canonical state.

Rejected full event sourcing as unnecessary complexity.

ADR commit for PostgreSQL/UUIDv7/provenance: `c7536e3cd522fbeda5bbd08aa73b4016d2516ac4`.

### Search/vector/graph

Selected:

- PostgreSQL full-text search initially;
- relational typed graph edges initially;
- dedicated search engine deferred until measured need;
- vector technology deferred until grounded-AI evaluation workload exists;
- specialized graph store deferred until measured traversal need.

Reason: semantics/provenance are canonical; indexes/projections must remain rebuildable.

### Durable background orchestration

Evaluated in-process tasks/simple queues versus durable orchestration.

Selected Temporal.

Current official Temporal Python documentation verified:

- Durable Execution;
- Activity retry policies/timeouts;
- idempotent Activity guidance;
- deterministic Workflow/event-history replay testing;
- Python async/sync Activity support.

Decision: multi-step source synchronization/reconciliation, acquisition/parse/evidence, AI and audio workflows use Temporal as the target durable orchestration layer. Ordinary request/response reads do not.

ADR commit: `9b25fbba8f993d138e673b79b1085bf85d4d9c8d`.

### Artifact/object storage

Selected an S3-compatible object-storage interface, private by default, while deferring the production vendor.

Required semantics:

- encryption at rest;
- signed time-limited access;
- content hashes/object metadata;
- lifecycle/retention classes;
- separation of reusable/restricted/user-private/generated objects.

Critical rule: storage capability never grants legal/rights permission. The Rights Engine decides retention/serving.

ADR commit: `9de5f56ed59faf85f0831e15f39f8de98adb5857`.

### Dependency/tooling

Selected baseline:

- `uv` for Python environment/dependency locking;
- `pnpm` for TypeScript/web locking;
- generated OpenAPI → TypeScript client drift checks.

Current uv documentation was checked for cross-platform lockfile/workspace behavior.

## Unresolved decisions/risks

1. Qualified legal review remains required before restricted/user-entitled/commercial derivative workflows.
2. Semantic Scholar commercial/broad persistent data use remains gated.
3. CORE commercial product use remains gated until applicable licensing is obtained/recorded.
4. Production hosting/cloud remains deferred.
5. Production S3-compatible object vendor remains deferred.
6. AI/TTS providers remain deferred until their evaluation phases.
7. Permanent parser/AI evaluation corpus licensing remains unresolved.
8. Formal accessibility target remains to be frozen before reader UI implementation.
9. Authentication and observability providers remain deferred.
10. Source contracts must be reverified if provider behavior/terms drift before or during implementation.
